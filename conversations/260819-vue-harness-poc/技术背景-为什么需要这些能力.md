# 技术背景：为什么一个 harness 类 agent 需要这些能力

> 写给"为什么要折腾 cordis/Vue reactivity，而不是 while 循环 + fetch 就完事"这个问题。
> 阅读对象：想了解这套架构动机的人。不需要提前读过 cordis 源码。
> 2026-08-19。

---

## 0. 起点：一个 coding agent 的"最小形态"长什么样

剥到底，一个 coding agent 就是一个循环：

```text
while (没做完) {
  回复 = 把对话历史发给 LLM（带上工具清单）
  if (回复里有工具调用) { 执行工具，结果塞回对话历史 }
  else break
}
```

这个循环五十行就能写完，而且能跑。事实上每个 agent 框架的内核都是它。那么问题来了：deepseek-harness 有五六十个 package，cordis 有一整套插件机制——**多出来的这些东西到底在解决什么问题？**

答案是：这个循环一旦要从 demo 变成产品，会撞上五堵墙。cordis 的每一项能力都对应一堵墙。下面逐堵说。

---

## 1. 第一堵墙：功能会越加越多，而它们都想插进循环里

最小循环写完之后，真实需求马上涌进来：

- 工具结果太长，要压缩（compaction）
- 危险操作要人审批（permission）
- 上下文要拼装系统提示（system prompt 是十几个来源拼出来的）
- 要记录会话、要统计 token、要限流、要埋点
- 要支持 MCP 外部工具、要支持定时任务、要支持子 agent

朴素的做法是往循环里加 if。加到第十个功能，循环就变成一团谁也不敢动的浆糊——每个功能都知道循环的内部细节，改一个坏一片。

**这就是"一切皆插件"要解决的问题**：循环本身只留骨架和扩展点，每个功能都是独立插件，只通过定义好的接口往循环上挂。harness 把这个原则推到极端——fs、tools、llm、session、loop 自己，全都是插件，走同一套挂载/卸载机制。好处不只是代码整洁：**当内核和功能用同一套机制时，agent 自己在运行时造的新功能（self-modification）也能用这套机制挂进来**，和用户装的功能平起平坐。这是后面第五堵墙的地基。

## 2. 第二堵墙：插件会动态地来和走，留下的垃圾没人扫

这是最容易被低估的一堵墙。demo 里插件是启动时装好、进程退出时一起死的。真实场景里插件的生命周期是动态的：

- 用户换模型 → llm 插件要换掉；
- agent 造了一个临时工具 → 用完要卸；
- 一个会话结束 → 这个会话注册的所有监听、定时器、文件句柄要回收；
- 插件自己崩溃 → 不能把整个运行时拖死。

每个插件活着的时候都会留下"副作用"：注册了工具、监听了事件、开了 watcher、往 UI 塞了组件。**插件死掉的那一刻，这些副作用必须全部、一个不剩地消失**——少回收一个事件监听，下次同样的事件就会触发两遍；少关一个 watcher，内存和句柄就漏了。

手动管理这件事几乎必然出错（每个插件作者都要记得写全清理逻辑，还得和注册逻辑保持对称）。cordis 的答案是把对称性做进机制里：**注册即副作用（registrations are effects）**。插件不能"裸"地改全局状态，它的一切对外影响都必须通过 `ctx.effect()` / `ctx.on()` 登记，登记的同时清理函数就被收走了。卸载时运行时逆序执行所有清理，插件作者想漏都漏不掉。

这就是为什么这个能力是"harness 架构的第一性原理"而不是锦上添花：**它把"清理"从每个插件作者的自觉，变成了运行时的强制保证。**

> Vue 对应物：`effectScope()` 干的就是这件事——scope 里创建的所有响应式 effect 在 `stop()` 时全部停掉。`onScopeDispose` 再补上非响应式的清理（定时器、监听器、句柄）。两者的差距只在异步清理（cordis 的 teardown 可以 await，Vue 的 stop 是同步的），这是 PoC 要手搓的第一块肉。

## 3. 第三堵墙：插件互相依赖，但启动顺序不该由人来排

tools 插件需要 fs，loop 需要 llm 和 tools，审批插件需要 interaction……真实的插件图有几十个点。谁来保证挂载顺序？

朴素做法：boot 脚本里手写顺序。这在小规模时能用，但有两个致命的延伸问题：

1. **可选能力**。某个 service 可能由用户配置决定装不装（比如没配 key 就没有 llm）。写了死顺序的 boot 无法表达"这个插件等那个 service，那个 service 可能永远不来"。
2. **运行期变化**。用户对话中途换模型，llm service 被替换——依赖它的 loop 插件该怎么办？继续用旧引用是错，直接崩也是错。

cordis 的答案是**声明式依赖 + 就绪驱动激活**：插件只声明"我需要 llm"，不满足就挂在 PENDING 不执行；service 出现了自动激活；service 被替换，依赖它的插件整体卸载重挂。启动顺序根本不是人排的，是从依赖关系推导出来的；运行期的服务替换也自动传播。

这个能力对 agent 产品特别重要，因为 agent 的配置空间天然是组合的：provider × 工具集 × 权限策略 × UI 形态，每个维度都可换。靠手工排序管理组合爆炸是不可能的。

> Vue 对应物：这里 Vue 反而更优雅。cordis 要手动维护"service 变了，通知所有依赖方重算"的机制；Vue 里把 service 注册表做成响应式的（`Map<string, shallowRef>`），插件体放进 `watchEffect`，**依赖追踪是自动的**——插件体里读了哪个 service 槽，哪个槽变了就自动重跑。手动 notify 整套省掉。代价是要守住一条纪律：状态都放在 service 里，插件体本身无状态，否则重跑会丢状态。

## 4. 第四堵墙：循环的关键节点需要被"包夹"，而不是只被"通知"

普通事件总线（emit/on）能表达"事情发生了，告诉一声"。但 agent 循环里最重要的扩展点不是通知型的，而是**拦截型**的：

- 发请求**之前**：compaction 插件想压缩上下文、prompt 插件想追加片段、guard 插件想拦下这次调用——它们要改的是请求本身；
- 工具执行**前后**：审批插件想在执行前弹确认，并且能**否决**这次执行；日志插件想在执行后记录；限流插件想让它排队。

注意"否决"这个词。审批不是"执行了然后告诉你一声"，而是"我说行才执行"。这要求扩展点是**中间件链**：每个插件拿到参数和 `next()`，可以选择改参数、调 next 放行、或者不调 next 直接短路返回。这就是 cordis 的 waterfall 语义（和 Koa/Express 中间件同构）。

为什么非要链式而不能是"一堆插件各改各的"？因为**顺序有意义**：审批必须发生在限流之后、执行之前；compaction 必须在 token 统计之后。链式结构让"我在谁的前面"成为显式的结构信息。harness 的 `agent/request`、`tools/pre|execute|post-execute` 全是 waterfall——可以说 agent loop 的骨架就是由这些拦截点定义的。

> Vue 没有对应物，这是 PoC 要手搓的第三块肉（约 40 行）。好消息是 waterfall 本身和响应式无关，是个纯函数编排问题，忠实复刻 next() 短路语义即可。

## 5. 第五堵墙：agent 要能给自己造轮子

这是 deepseek-harness 区别于普通 agent 框架的地方，也是这个项目的初衷：**agent 在运行时给自己造工具、造 UI、造插件，而且这些新东西和出厂功能地位完全平等**。

这件事听起来只是个"执行 agent 写的代码"的问题，实际难在**造出来的东西要有完整的生命周期**：

- 它注册的工具要能被后续对话发现（工具清单是动态生成的）；
- 它塞的 UI 组件要真的能渲染、能响应状态；
- 它崩了要有隔离，不能拖死宿主；
- 用户说"把这个卸了"，它的工具、UI、文件、事件监听要全部干净消失；
- 刷新页面，它应该还在（持久化 + 恢复）。

回头看，第 1-4 堵墙的答案恰好拼出这件事的地基：一切皆插件 → 新功能按插件挂；注册即副作用 → 卸载干净；就绪驱动 → 它依赖的服务就位后自动激活；waterfall → 它能插进循环的任何拦截点。**Self-modification 不是一个独立功能，它是前面所有能力到位之后自然溢出的结果。**反过来说，如果插件机制是临时的（比如用全局对象堆功能），agent 造出来的每个轮子都会成为一笔收不回来的债。

> 现有 boilerplate 已经验证了这条闭环：`create_plugin` 元工具 → 源码写 OPFS → Blob URL `import()` → 作为子插件挂载 → 刷新后扫描恢复。UI 侧用响应式组件注册表 + `<component :is>`，新组件即时可渲染。

## 6. 第六堵墙：状态更新不该靠人喊"我改了"

最后一堵墙最日常：agent 运行时的状态（消息流、文件树、工具清单、运行状态）变了，UI 要知道。命令式做法是每个改动点手动调刷新，漏一处就是"UI 和数据对不上"的 bug——这类 bug 在 agent 产品上极其高发，因为状态变化的源头又多又异步（流式 delta、工具回调、插件热插拔、后台任务）。

这正是 Vue reactivity 的主场，也是用 Vue 替代 cordis 时**白拿**的东西：服务注册表、消息数组、文件缓存全部是响应式的，UI 全部是 `computed`/模板绑定——**任何插件改了任何状态，UI 自动跟上，不存在"忘了通知"这种错误类别**。boilerplate 里文件树、消息流、动态组件槽、工具 schema 全是 computed，零手动通知，就是这条的直接证据。

cordis 自己其实没有这个能力（它不管数据层面的响应式），harness 需要数据响应时得自己想办法。所以"Vue 替代 cordis"不是等价替换，是**补上 cordis 本来就没有的一块，同时用手搓补它有的三块**。交换是划算的。

---

## 7. 总结：一张对照表

| 墙（真实痛点） | cordis 的答案 | Vue PoC 的对应 |
|---|---|---|
| 功能越加越多，都想插进循环 | 一切皆插件，循环只留扩展点 | 同哲学：内核即插件系统 |
| 插件动态来去，副作用残留 | 注册即副作用，卸载逆序全回收 | effectScope + onScopeDispose + 手搓 async teardown |
| 依赖组合爆炸，顺序没法手排 | 声明式 inject，就绪驱动激活 | 响应式 service 槽 + watchEffect，比原版更自动 |
| 关键节点需要可否决的拦截 | waterfall 中间件链 | 手搓 waterfall（~40 行） |
| agent 给自己造轮子 | 上面四条的总和 + loader/HMR | Blob import 造插件 + 响应式组件注册表（已验证） |
| 状态变了 UI 不知道 | （cordis 不管，harness 自理） | Vue 响应式，白拿 |

一句话：**这些能力没有一样是为了优雅而优雅的。每一样都对应 agent 从 demo 走向产品时必然会撞上的墙，而"agent 能改自己"这个终极目标，要求所有墙的地基必须是同一套机制。**这就是 cordis 设计哲学的价值，也是 PoC 要保留的东西——哪怕 API 长什么样完全另起炉灶。
