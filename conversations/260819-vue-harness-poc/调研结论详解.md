# 调研结论详解：用 Vue reactivity 做 deepseek-harness 的纯浏览器 PoC

> 写作时间：2026-08-19。本文是三个方向调研的完整记录，供后续任何 agent 或人接手时阅读。
> 一句话版本：**技术路线成立**。Vue reactivity 能接住 cordis 的骨架，pi-ai 能解决 LLM 接入，现有 boilerplate 方向正确、只需补几块肉。
> PoC 定位：**保留 cordis 的设计哲学（一切皆插件、注册即副作用、作用域级联回收、服务就绪驱动激活、拦截链扩展点），不追求 API 粒度对齐。**

---

## 第一部分：cordis 到底是什么

### 1.1 先看结论：它和你猜的"React 副作用管理 + 自动重载"半对半不对

对的那一半：cordis 的 `ctx.effect(fn)` 和 React 的 `useEffect` 确实是同一个东西——执行一个函数，收集它返回的清理函数，宿主销毁时把所有清理函数跑一遍。这一点完全同构。

不对的那一半：**cordis 没有细粒度的自动依赖追踪**。React 好歹还有依赖数组，cordis 连这个都没有。它的"依赖"指的是插件显式声明的 service 名字（`static inject = ['llm']`），而不是数据。数据变了自动重跑这种事在 cordis 里不存在。它的重跑粒度是整个插件体：依赖的 service 变了，就把这个插件的所有副作用全部卸载，然后整个插件函数重新跑一遍。

这里有个挺讽刺的发现：Vue 的 `watchEffect` 自动追踪模型反而比 cordis 更接近"自动版 useEffect"。所以用 Vue 替代的时候，service 可用性做成 `shallowRef`，依赖方自动重跑，cordis 那套手动 notify/epoch 调度机制可以直接省掉。**替代之后得到的东西在某些维度上比原版更自动。**

### 1.2 cordis 的全部能力（core 包只有 8 个文件，值得记住的都在这）

整个 cordis 围绕两个概念：**Fiber（插件的运行实例）** 和 **Context（原型链串起来的服务仓库）**。

1. **插件注册与卸载**。`ctx.plugin(plugin, config)` 把插件挂上去，生成一个 Fiber 挂在父 Fiber 下面。插件可以是函数、类、或者带 `apply` 方法的对象。`fiber.dispose()` 把这个插件的全部副作用按**逆序**（LIFO）异步卸载掉。

2. **Fiber 状态机**。插件不是注册即运行的。它经过 PENDING → LOADING → ACTIVE →（可能 FAILED）→ UNLOADING → DISPOSED。inject 的 service 没齐就停在 PENDING；齐了才执行插件体。调 `fiber.update(config)` 改配置会校验后整体重启。

3. **声明式依赖注入**。插件声明 `static inject = ['systemPrompt', 'llm']`，cordis 在 service 注册/注销时遍历所有 Fiber，重算每个插件的依赖是否满足，不满足的卸掉、满足了的挂起来。**插件的加载顺序完全由 service 依赖推导，没有任何手动排序。**

4. **服务注册**。`ctx.provide(name, value)` 往注册表登记；`Service` 基类的子类一构造就自动 provide 自己。provide 本身也是一个 effect——提供服务的插件被卸载时，服务自动撤回。

5. **副作用生命周期**。`ctx.effect(fn)` 执行 fn 并收集清理函数。支持四种形式：同步函数、返回 Promise 的函数、同步生成器、异步生成器（生成器每 yield 一个值就是一个 disposer）。teardown 全程可以 await，还带 label 可以自省（`getEffects()` 列出活着的副作用）。

6. **事件总线，五种派发模式**。`emit`（不管结果）、`parallel`（并发等所有）、`serial`（排队）、`bail`（有返回值就停）、**`waterfall`**（中间件链，每个监听器拿到 `(...args, next)`，不调 next 就短路）。waterfall 是 harness 的命脉，后面细说。

7. **上下文树**。`ctx.extend()` 用 `Object.create` 派生子上下文，子上下文的服务查找沿原型链往上走。`ctx.isolate(name)` 让同名 service 在子树里解析到不同实例（隔离域），`ctx.intercept` 分层覆盖配置。这两个在 harness 里几乎没被直接用，属于边缘能力。

8. **配置校验**。插件可以带一个 `Config` schema，挂载和更新时同步校验，失败进 FAILED 态。

9. **HMR（独立的 hmr 包）**。监视文件变化 → 沿模块依赖图分析 → 清缓存 → 重新 import → 用**旧 config** 重新挂载新代码。Node 端实现很脏（要碰 ModuleLoader internals 和双缓存清除），但这是 cordis 自己的能力，不是 Fiber 模型的必需品。

10. **loader/include（独立包）**。从 `cordis.yml` 配置文件挂载整棵插件树，支持 profile 分层和 patch 覆盖。这是 harness 的发布形态（用户靠改 yml 定制产品），不是运行时语义。

### 1.3 deepseek-harness 实际用了 cordis 的哪几成功力

统计 harness 全部 packages 里的 API 调用次数：`ctx.on` 196 次、`ctx.effect` 169 次、`extends Service` 68 次、`ctx.plugin` 54 次、`ctx.inject` 43 次、`ctx.emit` 27 次、`ctx.provide` 19 次、waterfall 13 次。而 `ctx.isolate`、`ctx.intercept`、`fiber.restart` 在整个 TS 代码里**一次都没有直接出现过**。

所以 harness 真正重度依赖的 cordis 能力是五样：

1. **Service DI + 声明式 inject**——一切皆是插件，插件靠声明 service 依赖来决定何时激活；
2. **"注册即副作用"（registrations are effects）**——工具 schema、prompt 片段、事件监听全部通过 `ctx.effect()` / `ctx.on()` 注册，插件一卸载全部自动回卷。这是 harness 架构的第一性原理，写在 AGENTS.md 里；
3. **waterfall 事件中间件**——`agent/pre-step`、`agent/request`、`llm/stream`、`tools/pre|execute|post-execute` 都是 waterfall 链，是 agent loop 的核心扩展点；
4. **per-agent 作用域**——每个 agent 会话拿一个专属 Fiber（轻量子上下文），其注册随 agent 销毁而回收；
5. **配置树组合**——boot 就是建 root context、装 loader、按 yml 挂插件树。

**结论：harness 对 cordis 的依赖恰好落在 Vue 能覆盖或低成本手搓的范围内。它不依赖 cordis 最难替代的部分（Node HMR 内部机制、yml loader）。**

## 第二部分：cordis → Vue reactivity 的映射

在 vue-core 源码（`packages/reactivity/src`）里核对过：EffectScope 有父子 scope 树，`stop()` 同步清掉所有 effect 和 cleanup，`onScopeDispose` 注册清理回调，`watch` 的回调里能拿 `onCleanup`。注意 `provide/inject` 在 runtime-core 里、绑死在组件实例上，脱离组件树用不了，得自己造。

| cordis 原语 | Vue 对应物 | 判定 | 说明 |
|---|---|---|---|
| `ctx.plugin()` 挂插件 | `effectScope()` + `scope.run()`，`scope.stop()` | **能（骨架）** | 父子 scope 树、嵌套停止、停止时清全部 effect，结构同构。缺插件注册表和状态机 |
| `ctx.effect(fn)` | `scope.run(fn)` 内 `onScopeDispose(cb)`，或 `watchEffect((onCleanup) => ...)` | **能（核心语义）** | 同步 disposer 完全等价 |
| async disposer、可 await 的 teardown | 没有。`stop()` 同步返回，cleanup 返回值被忽略 | **需手搓** | 在 scope 外包一层"disposal 队列 + Promise 汇总"。这是最大的语义缺口 |
| 声明式 inject（不齐就等、就绪自动重跑） | services 做成 `shallowRef` 注册表 + `watchEffect` 自动重跑 | **需手搓，但比 cordis 优雅** | 自动追踪替代手动 notify。但状态保留要靠纪律：state 全放 service，插件体本身无状态 |
| `ctx.provide` 服务仓库 | 组件外用不了 provide/inject，手搓 `Map<string, shallowRef>` | **需手搓（小）** | 百行以内的类型化 DI 容器 |
| `emit/on/once` | reactivity 没有事件总线 | **需手搓（小）** | 普通 emitter，`ctx.on` 挂 scope 上自动注销 |
| waterfall 等四种派发 | 没有 | **需手搓（中）** | waterfall 必须忠实复刻 `next()` 短路语义 |
| per-agent 子上下文 | 没有；嵌套 effectScope + 每 scope 一个覆盖 Map | **需手搓（小）** | harness 用得少，就近覆盖即可 |
| 配置校验 | zod / valibot | **能** | StandardSchema 生态平替 |
| Fiber 状态机 | 没有 | **需手搓（中）** | 每个插件一个 `ref<state>`，调错和 UI 展示都要用 |
| HMR | Vite `import.meta.hot.accept` | **需手搓，但浏览器端反而简单** | cordis-hmr 最脏的部分（ModuleLoader internals）由 Vite 代劳，只需编排"旧 scope.stop() → 旧 config 重跑新模块" |
| yml 配置树 | 没有浏览器等价物 | **不做** | PoC 直接用 TS 代码组合插件，声明式配置是产品形态问题，不是内核问题 |

**总体判断**：EffectScope 和 Fiber 是同构设计，骨架直接对上。要补的三块肉按优先级：**异步 teardown 编排、声明式 inject 的等待/重跑调度、waterfall 事件链**。补完后得到的是一个比 cordis 更自动的内核（依赖追踪免手工），代价是放弃 cordis 实战打磨过的边界行为（错误隔离细节、introspection 工具）——对 PoC 来说这个交换很划算。

## 第三部分：纯浏览器 coding agent 的现有做法

调研了 pi-mono（重点深读）、bolt.diy、nanobrowser。pi-mono 已浅克隆到 `ref_repos/pi-mono/`（注意 npm 包名已从 `@mariozechner/*` 改为 `@earendil-works/*`）。

### 3.1 pi-ai：直接用它，不要手搓 adapter

pi-ai 的统一抽象是 **API 协议 × Provider** 二维拆分：10 种协议（anthropic-messages、openai-completions、google-generative-ai 等）各是一个模块，实现统一的 `stream(model, context, options)` 签名；35+ 家 provider 各自只是"baseUrl + 模型目录 + 鉴权"绑定到某个协议。DeepSeek 就是 openAICompletionsApi 配 `https://api.deepseek.com`。

几个对 PoC 最关键的事实：

- **官方明确支持浏览器**。Anthropic adapter 里写死了 `dangerouslyAllowBrowser: true`，各家 SDK 在浏览器可用，Node-only 的部分被刻意隔离（环境变量解析、Bedrock、OAuth），浏览器调用时运行期报错而不影响打包。
- **BYOK 的正解**：`options.apiKey` 显式传入，key 存 localStorage，不走环境变量。
- **stream 抽象是最值钱的设计**：一个手写 push-queue 的 AsyncIterable，`for await` 消费事件，事件粒度细到 `text_delta`、`toolcall_delta`，而且**每个事件都携带累积中的完整消息快照 `partial`**——UI 不用自己拼 delta，`Object.assign(msg, ev.partial)` 就完事。
- **`Model.compat` 字段**吸收各家 API 的怪异行为（thinking 格式 ×10、strict tools、cache_control）。这是多年踩坑积累，手搓等于重踩一遍。
- 分包 tree-shaking 友好：`pi-ai/providers/deepseek` 按需引，SDK 走 lazy chunk。

### 3.2 pi-agent-core：可选，先直接用它

agent loop（约 800 行）就是两层 while：外层处理用户 follow-up，内层处理 tool call 循环（stream → 收集 toolCall → 执行 → 结果回填 → 继续 stream）。事件用 `AgentEvent` 联合类型暴露（`message_update` 携带流式事件、`tool_execution_start|update|end` 等），callback 和 AsyncIterable 双通道。FileSystem/Shell 是抽象接口，Node 绑定集中在一个文件里——换成浏览器实现即可。

建议：**PoC 阶段直接依赖 pi-ai，loop 可以参考 pi-agent-core 的事件设计自己写**（约 200 行），因为我们要让 loop 和 Vue 状态深度耦合（reactive 消息流、stop 按钮、插件系统拦截链），自写反而顺手。pi-coding-agent（CLI 本体）是 Node-only，不可复用，只参考它的 system prompt 和工具 schema。

### 3.3 其他项目给的启发

- **bolt.diy**（开源 bolt.new）：LLM 走 Vercel AI SDK，BYOK 的 key 存 cookie 发给自家 server route 再转发——同源 mini-proxy 模式，纯静态站用不上。虚拟 FS 用 WebContainers（WASM Node），对 PoC 过重。
- **nanobrowser**（Chrome 扩展）：key 存 `chrome.storage.local`，在 service worker 里直连各家 API，扩展的 host_permissions 天然绕过 CORS。印证了"如果走 userscript/扩展形态，CORS 问题自动消失"。
- **裸 fetch 直连**：Anthropic 需要 `anthropic-dangerous-direct-browser-access` 头；DeepSeek/Moonshot/OpenRouter 这类 OpenAI 兼容端点一般允许浏览器跨域，但要真机验证。

### 3.4 流式 × Vue 的推荐模式

```ts
const msg = reactive({ content: [], status: 'streaming' })
messages.push(msg)

const stream = provider.stream(model, context, { apiKey, signal })
for await (const ev of stream) {
  Object.assign(msg, ev.partial)   // 事件自带累积快照，整体替换
  if (ev.type === 'done' || ev.type === 'error') msg.status = ev.type
}
```

要点：别自己拼 delta；`AbortController` 的 signal 透传进去，stop 按钮就是 `controller.abort()`；thinking/text/toolCall 按 contentIndex 分块渲染。

## 第四部分：现有 boilerplate（app/index.html，553 行）的评估

### 4.1 它实际实现了什么

| 模块 | 行数规模 | 完成度 | 说明 |
|---|---|---|---|
| 插件运行时 `createContext()` | ~40 行 | ✅ 真可用 | cordis 最小复刻：服务槽 `shallowRef`、每插件一个 `effectScope`、dispose = scope.stop() + LIFO 清理栈、插件体异常隔离、级联卸载 |
| fs 插件（OPFS） | ~50 行 | ✅ 真可用 | 写穿透缓存（reactive Map 做读侧），启动时预载恢复，不支持 OPFS 时降级内存 |
| tools + 三个内置工具 | ~90 行 | ✅ 真可用 | 工具即子插件，热插拔兑现；file_editor / run_js（Worker 沙箱 + 5s 超时）/ create_plugin；工具错误以字符串返回（模型友好） |
| llm + loop | ~60 行 | ⚠️ 薄 | OpenAI 兼容协议直连 DeepSeek，**非流式**整包 fetch；无 AbortController（stop 是假停）；注释自称 PENDING 实际是运行时手动判空 |
| self-modifying（create_plugin + widgets） | ~100 行 | ✅ 真可用 | 运行时造插件（Blob URL import + OPFS 持久化 + 启动恢复）+ 运行时造组件（template 字符串 + `<component :is>`），闭环完整 |
| session | 3 行 | ⚠️ stub | 自称 append-only 日志，实际就是内存数组，无持久化无 resume |
| UI | ~120 行 | ✅ 可用 | 五面板两栏 grid，全部 computed 驱动，零手动通知 |

### 4.2 和理论的一致与偏离

**一致的**（理论被正确兑现）：响应式白拿状态更新、effectScope 对应插件作用域、一切皆插件、Creator 模式闭环、级联卸载。

**偏离的 / 缺口的**：

1. **声明式依赖与 PENDING 语义缺失**——这是和 cordis 能力模型差距最大的一处；
2. **热替换不保状态**——`create_plugin` 同名重建会先 dispose 旧 fiber，组件内 ref 状态全丢。理论里的迷你 HMR 保状态在任何一处都没兑现（注意：报告 §2.3 的三行 HMR 是针对改写**宿主站点**组件的 C 级能力，改自己的 UI 用 `<component :is>` 就够了，所以这不是缺陷，但"保状态"确实没有）；
3. **dispose 同步、stop 假停**——异步清理无人 await，in-flight fetch 不会被取消；
4. **事件系统整体缺席**——没有 ctx.on/emit，没有 waterfall，审批/拦截无挂点；
5. **session 名不符实**；**LLM 非流式**；
6. 两个硬伤级的便宜修复：`import(blob:)` 在 Safari 不可用（加 `new Function` 降级约 10 行）、stop 接 AbortController（约 5 行）；
7. 小瑕疵：`ctx.log` 的滚动逻辑直接 getElementById，违反"运行时与 DOM 无关"的承诺；inject 的 parent 链遍历是死代码（所有服务都注册在根）。

### 4.3 总体评价

这份 boilerplate 不是样子货。553 行里有效代码密度很高，错误隔离、时序 await、模型友好的错误回传都做了。它相对理论的缺口集中在 cordis 的硬核部分：声明式依赖、异步 dispose、事件链——恰好就是第二部分映射表里标"需手搓"的那三块肉。

## 第五部分：PoC 的目标架构（保留 cordis 设计哲学，不对齐 API）

### 5.1 什么是"设计哲学"，什么是"API 粒度"

PoC 要保留的哲学（缺一不可）：

1. **一切皆插件**——fs、tools、llm、loop、session、UI 槽位都是插件，走同一个挂载/卸载机制；
2. **注册即副作用**——插件的一切对外影响（注册工具、注册服务、监听事件、写文件）都通过 effect 登记，卸载时全部自动回卷，不允许"裸奔"的全局修改；
3. **作用域树与级联回收**——插件挂成一棵树，父死子亡，清理逆序执行；
4. **服务就绪驱动激活**——插件声明依赖，依赖没齐就不跑，齐了自动跑（Vue 版用响应式实现，比 cordis 手动 notify 更自动）；
5. **拦截链作为扩展点**——agent loop 的关键节点（请求前、工具执行前后）暴露 waterfall 式钩子，插件可以插进来改写行为；
6. **运行时自修改**——agent 能给自己造插件、造组件，且持久化后刷新仍在。

不需要对齐的 API 粒度：函数签名、配置 schema 格式、yml loader、状态机的具体状态名、cordis 的 isolate/intercept 机制、HMR 的内部实现——全部按"浏览器 + Vue 习惯"重新设计，怎么简单怎么来。

### 5.2 建议的 PoC 形态

在现有 `app/index.html` 基础上演进（或重开一个 Vite 工程，见 handoff 文档的决策点），核心 JS 约 300-400 行：

- **插件内核 ~80 行**：context = effectScope + 服务注册表（`Map<string, shallowRef>`）+ effect 清理栈（支持 async disposer 的 Promise 汇总）+ plugin()（子 scope、异常隔离、级联卸载）。比现状多出来的 40 行就是异步 teardown 和声明式 inject 的 watchEffect 调度；
- **事件总线 ~40 行**：emit/on 挂在 scope 上自动注销，waterfall 带 next() 短路；
- **LLM 层**：pi-ai 直连 DeepSeek（BYOK，localStorage 存 key），流式事件灌 reactive 消息对象，AbortController 真停止；
- **loop ~100 行**：tool call 循环，关键节点过 waterfall，stop 真停；
- **fs 插件**：维持 OPFS（已经写好了，砍了反而浪费），或降级 localStorage 快照（15 行）；
- **self-modifying**：维持 Blob import + `new Function` 降级，插件源码落 OPFS。

### 5.3 明确的非目标（PoC 不做）

- 多 agent / subagent 并行；
- 会话持久化与 resume（session 插件保持内存数组即可，别留名不符实的壳——要么不做，要么做真的）；
- 权限审批系统（waterfall 挂点留好就行）;
- yml 配置树、插件市场、profile 分层；
- 寄生任意 Vue 网站（那是报告里的后续方向，PoC 先把自己的运行时做扎实）。
